## 2. 日時・時間窓の仕様

- 時刻はすべて UTC です。入力欄も UTC の値を表示し、端末の時差に変換しません。URL の時刻は `2026-03-10T12:00Z` の形で、時差付きの値は読みません。
- 時間窓は半開区間 [開始, 終了) で、便の `referenceTime`（航跡開始、なければ航跡終了）で判定します（Phase 9A と同じ）。
- 期間の種類：1日（既定）、暦月、直近 7日・24時間・6時間・1時間、任意の期間。移動幅（1時間・6時間・1日・7日）は期間と独立に選べます（暦月は1か月単位）。
- データの範囲外にかかる期間は範囲内に切り詰め、「データの端で切り詰め」と表示します。範囲外だけの期間は「データの範囲外」と表示し、値を作りません。

## 3. 10日超の期間への対応

Phase 9A のローダーは 1 つの窓で 10 日までに制限していました。Phase 9B では Web Worker で 1 日ずつ読み、方向・航空会社・根拠区分・機材分類ごとの便数に足し込みます（`WindowAggregator`）。

- 読み込んだ日は LRU で最大 14 日分だけ保持し、それより長い期間でも使用メモリは増えません（集計結果は路線×方向×航空会社×区分×分類の行だけ）。
- 新しい要求が来ると、古い要求は日と日の間で打ち切ります（`SupersededError`）。
- 進捗（読み込んだ日数／全体）をタイムラインに表示します。
- 2026年3月の 31 日分を集計した結果は月次データと完全に一致します（テスト `temporalData.test.ts`、ブラウザでも路線 58,508・空港 3,883・便 2,505,703 で一致）。

## 4. 時刻品質フィルター

- 「すべての便」：`TRACK_START` と `TRACK_END_FALLBACK` の両方（月次と同じ定義）。
- 「航跡開始時刻のある便のみ」：`TRACK_START` だけ。除いた便数と割合を表示し、「航跡開始は離陸時刻とは限らない」と注記します。
- どちらでも、期間内の航跡終了で代用した便の割合を表示します。
- Research Mode の時間窓でも同じ選択ができ、条件（ハッシュ）に含まれます。

## 5. 地図・地球儀との連携

時間窓の集計結果を月次と同じ `MonthData`（路線×方向×航空会社×旅客・貨物・不明×根拠）に変換して渡します。このため、絞り込み、空港の選択、路線の強調、ランキング、月次比較の色分けなど既存の処理をそのまま使い、描画用のバッファ・WebGL のレンダラーは作り直しません（平面地図と地球儀を切り替えても canvas は 1 つのまま、再集計なし）。比較期間の結果と表示中の期間の結果は 1 回の状態更新で同時に差し替えるので、ある期間に別の期間の比較が重なることはありません。

## 6. 再生機能

- 再生・一時停止・前へ・次へ・先頭へ、速度 3 段階、ループ。
- 次の期間へ進むのは、今の期間の集計が終わって画面に出てから一定時間後です。集計が遅い期間では待ちます。
- 再生中に日付・期間・条件を変えると再生は止まります。
- 次の期間に必要な日（最後の 2 日）を先に読み込みます。
- タイムラインの数値は「表示中の期間と同じ期間の結果」のときだけ表示し、集計中は「…」または進捗を表示します。

## 7. Research Mode との統合

- 設定の「期間」で暦月／時間窓（UTC）を切り替えます。時間窓では同じ日別ファイルから同じ集計で `ResearchMonth` を作り、既存のネットワーク構築・指標計算（Web Worker）をそのまま使います。
- 重い指標は再生の各ステップでは計算しません（Research Mode で明示的に分析したときだけ）。
- キャッシュのキーとハッシュには期間が入ります。暦月の条件では `window` をハッシュの計算から外しているので、Phase 8 で出力した JSON・URL のハッシュは変わりません（テストで Phase 8 時点の値と照合）。
- 前の期間（同じ長さの直前の期間）の便数を路線表の比較に使い、比較タブでは直前・1日前・7日前の期間と比べられます。
- 表示の調整：題名に期間、閾値の名前「選択期間内に観測された路線ごとの便数」、「1日あたり」の代わりに「1時間あたり」、24時間未満の注意、期間にかかる収集欠損の警告、外部統計とは照合しない旨。
- 「Research Modeで分析」「地図で表示」で Explore と Research の間を同じ期間のまま行き来できます。

## 8. 観測品質の表示

- 状態 A〜E（観測ゼロ、収集欠損の疑い、ファイルなし、読み込み失敗、絞り込み後ゼロ）を区別して表示します。判定は `windowQuality()`（純粋関数、テストあり）。
- 収集欠損の時間は、Phase 6B で収集欠損と判定した日の中で、世界の便数が 100 未満の時間です（通常は 1 時間あたり 2,500〜5,000 便）。5月5日〜7日の窓では「66 時間」と表示し、5月7日 18 時以降は欠損にしません。
- タイムラインの帯に欠損の疑いのある日（橙）と通常と異なる日（灰）を表示します。
- 時間変化の図では欠損の時間帯を塗り、「空白は観測の欠落」と注記します。
- 時刻の品質として、期間内の航跡終了で代用した割合と、データ全体の大陸別の航跡開始の欠落率を表示します。
- 観測されなかった路線を「廃止」とは呼びません（比較では「もう片方で観測されなかった」と表示）。

## 9. データロードとキャッシュ

| 層 | 内容 |
| --- | --- |
| HTTP | GitHub Pages：gzip（`Content-Encoding: gzip`、`Cache-Control: max-age=600`）。Brotli は要求しても返らないことを確認 |
| 日のキャッシュ（Worker） | 解凍・展開した日を LRU で最大 14 日 |
| 結果のキャッシュ（メイン） | 同じ期間・条件の集計結果を LRU で 8 件 |
| 先読み | 次の期間の最後の 2 日 |
| 取り消し | 系統（Explore、比較、Research の現在・前の期間）ごとに新しい要求が古い要求を置き換える |
| メタデータ | `index.json`・`manifest.json`・`quality.json` は時間窓を初めて開いたときに 1 回だけ |

時間窓を開かなければ、時間軸のファイルは一切読み込みません。

## 13. 未解決の問題

- 描画フレームの時間（F）と Worker のメモリは実測できていません（ブラウザの画面が非表示、Worker のメモリを測る API がない）。
- 14 日より長い期間を再生すると、ステップごとに日別ファイルを読み直します（1 ステップ 1〜3 秒、1 か月で約 7 MB の転送）。
- 「その時間に飛んでいた可能性のある便」（航跡が期間と重なる便）は実装していません。日別ファイルは基準時刻だけを持つため、研究用データから別のファイルを作る必要があります。
- Research Mode の「継続性（観測された月数）」は時間窓でも月次データを使います。
- Explore の時間窓の状態は URL で共有できますが、JSON での保存は Research Mode の分析条件だけです。
- 外部統計（月次）との照合は時間窓では行いません。
- 狭い画面では時間窓のタイムラインが画面の下を広く使います。

## 14. Phase 9C への引き継ぎ

- イベントの型：`src/temporal/scenario.ts`（`eventId`、`eventType`、`startTime`、`endTime`、`affectedAirports`、`affectedRoutes`、`source`、`sourceUrl`、`isHypothetical`）。安全勧告と閉鎖は別の種類で、`removesCapacity()` は勧告では false。
- 変換を入れる場所：`WindowAggregator.rows()`（観測の集計結果）と `toMonthData()`／`toResearchMonth()` の間。行を受け取り新しい行を返す純粋関数にすれば、観測データは変わらず、地図・Research の分析をそのまま使えます。
- 時刻：イベントの時刻は ISO 8601（UTC）、時間窓との重なりは `eventOverlaps()`（半開区間）。
- 比較：同じ期間の「観測」と「シナリオ適用後」を、既存の比較（`baseMonth`／Research の比較）で並べられます。
- 必要になる変更は「Phase 9C に向けて必要な変更」（最終報告の E）にまとめています。
