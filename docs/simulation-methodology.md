# シミュレーションの計算方法（研究者向け）

1090web のシミュレーション（Phase 9C）の定義・仮定・指標をまとめます。実装は `src/simulation/`、使い方は [simulation-guide.md](simulation-guide.md)、実装の記録と実測値は [phase9c-report.md](phase9c-report.md) にあります。

## 1. 位置づけ

観測された ADS-B のネットワークに仮想的な障害（空港・路線の停止）を適用し、ネットワークの構造がどう変わるかを調べる道具です。

- 欠航数・旅客数・航空会社の運航・振り替えの予測ではありません。
- 観測データは変更しません。シナリオは独立したデータ（JSON）で、同じデータセット・同じシナリオからは同じ結果が出ます。
- 処理の流れ：観測データ → 基準ネットワーク → シナリオ定義 → シナリオ適用 → シミュレーション後のネットワーク → 影響分析 → 表示・出力

## 2. シナリオ

| 項目 | 内容 |
| --- | --- |
| `baselineMode` | `fixed`：基準期間 [analysisStart, analysisEnd) の観測ネットワークを固定／`dynamic`：時間窓の表示の各期間 |
| `simulationModel` | `structural`（構造）／`temporal`（時刻照合） |
| `evaluationTime` | 構造・固定のとき、この時刻に有効なイベントだけを適用（なし＝期間と重なるイベントすべて） |
| `events[]` | `AIRPORT_CLOSURE`・`MULTIPLE_AIRPORT_CLOSURE`・`ROUTE_SUSPENSION`（下表）。ほかの種類は保持するが適用しない |
| `filters` | 根拠区分（T1〜T4 の組）、機材分類、基準期間の最低観測便数、時刻基準（全便／航跡開始のみ）、時刻プロキシ |
| `analysisSettings` | 有向／無向、Research Mode の中心性の計算方法 |

イベント：

| 種類 | 対象 | `direction` |
| --- | --- | --- |
| `AIRPORT_CLOSURE`／`MULTIPLE_AIRPORT_CLOSURE` | 空港 ID（複数可） | `both`（出発と到着）・`departures`・`arrivals` |
| `ROUTE_SUSPENSION` | `"A>B"` | `both`（双方向）・`directed`（A→B のみ） |

期間は UTC の半開区間 [start, end)、分単位です。`null` は開始・終了を限定しないことを表します。`SAFETY_ADVISORY`（安全勧告）は記録できますが、閉鎖ではないので何も取り除きません。

## 3. シナリオの適用（順序に依存しない方法）

1. 有効で不正のないイベントだけを取り出す（存在しない空港・路線、終了 ≤ 開始の期間、未対応の種類は理由を表示して適用しない）。
2. 「空港の出発側」「空港の到着側」「路線の各方向」ごとに、停止区間の和集合を作る（重なる・接する区間は結合）。
3. 便（または路線の方向）は、この和集合に1つでも該当すれば影響対象。複数のイベントに該当しても1回だけ数える。

和集合はイベントの集合から決まるので、イベントの順序を変えても、同じイベントを重ねても結果は同じです（冪等・可換）。テストで確認しています。

**将来の非可換な操作の順序**（容量削減率など、未実装）：(1) 停止（この和集合）を先に適用し、(2) 残った便に容量の係数を、開始時刻の早い順・同時刻ならイベント ID 順に掛ける、という順序を想定しています。導入時は順序をシナリオに明記します。

## 4. 構造分析（Structural Simulation）

基準期間のネットワークから、停止した空港の該当する側（出発・到着）の便と、停止した路線の方向を取り除きます。

- 固定の基準＋評価時刻あり：その時刻に有効なイベント。評価時刻なし：期間と重なるイベント。
- 時間窓に連動：その時間窓と重なるイベント（その窓の間ずっと停止していると仮定）。
- 「利用できない接続上の観測便数」は、取り除いた接続上の期間中の観測便数です。障害の時刻に実際に欠航した便数ではありません。

## 5. 時刻照合（Temporal Disruption）

集計前の便の記録ごとに判定します。日・月の集計値から重なりの割合を差し引く方法は使いません。

### 時刻プロキシ

| 設定 | 出発側の時刻 | 到着側の時刻 |
| --- | --- | --- |
| `endpoint`（既定） | 航跡開始（開始時刻のない便は不明） | 航跡終了（終了時刻のない便は不明） |
| `reference` | 基準時刻（航跡開始、なければ航跡終了） | 同じ基準時刻 |

- 空港 X の停止：出発空港が X で出発側の時刻が停止区間内、または到着空港が X で到着側の時刻が停止区間内の便。
- 路線の停止：その方向の便で、基準時刻が停止区間内の便。
- 停止した側の時刻が不明で、もう一方の時刻からみて停止区間に入りうる便（航跡は最長 24 時間と仮定）は「判定不能」として数え、除外しません。
- 分析の対象は、基準時刻が分析期間に入る便です（Phase 9A・9B と同じ）。

航跡の開始・終了は離着陸時刻ではありません。結果は「時刻プロキシによる影響候補」です。

### 到着側の時刻のデータ

公開用の日別ファイル（Phase 9A）は基準時刻しか持たないため、空港の到着側を正しく判定できませんでした。Phase 9C で、研究用 Parquet の航跡終了時刻から、日別ファイルと同じ順序の補助ファイル `temporal/endpoints/YYYY-MM-DD.json` を作りました（`pipeline/temporal_endpoints.py`）。

- 値：基準時刻の分から航跡終了の分までの分数（各時刻を分単位で切り捨て）。不明は −1（開始時刻がない便、終了時刻がない便、終了が開始より前の便）。
- 生成時に、全 273 日について日別ファイルの便の並び（路線・分・航空会社・区分）と一致することを照合します。日別ファイル自体は変更していません。
- 2026年1〜9月：2,290 万便のうち航跡終了が分かるのは 1,993 万便。容量は 77.7 MB（gzip 26.7 MB、1日あたり約 98 KB）。

### 例（実データ、2026-03-10 に OMDB を 12:00〜18:00 停止）

| 選び方 | 便数 |
| --- | --- |
| OMDB に発着する便（3月10日の基準時刻） | 369 |
| 基準時刻が 12:00〜18:00 の便（`reference`） | 130 |
| 出発側（航跡開始）か到着側（航跡終了）が 12:00〜18:00 の便（`endpoint`） | 56（出発 30、到着 26） |

研究用 Parquet から DuckDB で独立に数えた値と一致します。`reference` が多いのは、12時〜18時に出発して停止の後に到着した便を到着側でも数えてしまうためです。

## 6. 基準ネットワーク

両方のネットワークを Research Mode のネットワーク構築（`buildResearchNetwork`）で同じ条件から作ります。最低観測便数は基準ネットワークの路線を選ぶためだけに使い、シミュレーション後は基準の路線のうち便が1便以上残るものを残します（一部の便が影響を受けた路線が、閾値を下回ったというだけで消えないように）。

- **固定**：時間を進めても基準ネットワークは変わりません。観測便を別の日付に移すことはしません。
- **時間窓に連動**：各時間窓を、同じ時間窓の観測ネットワークと比べます。窓どうしの差は障害の影響とは限りません（観測そのものが違うため）。

## 7. 影響指標

### 直接の影響

停止した空港、接続を失ったほかの空港、失われた直接接続（無向・有向）、便数が減った接続、影響対象の観測便数（構造：取り除いた接続上の便、時刻照合：停止区間に入る記録）、航空会社コード別、出発空港の地域・国別。

### 接続性（全空港からの幅優先探索、厳密）

経路はホップ数（重みなし）です。便数を距離として使いません。

- 到達可能な組、1・2・3ホップ以内の組（2ホップ＝中継空港1つ）
- ネットワーク効率 E(G) = 1 / [N(N−1)] × Σ 1/d(i, j)（到達不能は 1/d = 0）。Research Mode の調和近接中心性（正規化）の全空港平均と同じ定義です（テストで一致を確認）。
- 連結成分（弱連結、孤立した空港を含む）と最大連結成分
- 有向では、A→B に到達できても B→A に到達できるとは限りません。

### システム全体と波及（分母の扱い）

| | 対象の空港 | 分母 | 障害前の経路 |
| --- | --- | --- | --- |
| システム全体 | 基準ネットワークの全空港 N（停止した空港を含む） | N(N−1)（前後で同じ） | 基準ネットワーク |
| 波及 | 停止対象以外の空港 | その空港の組（停止した路線の組を除く、前後で同じ） | 基準ネットワーク（停止対象を経由してよい） |

停止した空港はシミュレーション後も「孤立した空港」としてノード集合に残します。空港をノード集合から除くと分母が小さくなり、効率が見かけ上上がることがあるためです。波及は「停止対象を経由できなくなったことで、ほかの空港どうしが失ったもの」を表します。路線の停止では停止ノードがないため、停止した空港の組だけを波及の評価から除きます。

### 空港別

接続先数、到達可能な空港数（停止対象を除く）、2・3ホップ以内の空港数、到達できなくなった相手の数、経路が長くなった相手の数と増えたホップ数の合計。

### 代替経路

選んだ空港の組について、中継空港を共有しない最短経路を最大3つ（前の経路の中継空港を除いて探索。直接便がある場合は、その直行の辺を除いて次を探索）。グラフ上の経路で、時刻・座席・航空会社間の乗り継ぎを保証しません。

## 8. Research Mode との統合

分析条件に `scenario`（モデル、評価時刻、時刻プロキシ、イベント）を持たせ、同じ適用処理で作ったネットワークに既存の指標（次数、重み付き次数、媒介中心性、調和近接中心性、PageRank、連結成分、密度、クラスタ係数）を計算します。比較タブの「シナリオ」で、シナリオなし（観測）と比べます。

- 空港が除かれるとノード集合が変わるため、密度とクラスタ係数は増減率で比べません（表示しない）。
- `scenario` がない条件のハッシュは Phase 8・9B と同じです。

## 9. 観測上の問題とシミュレーション上の仮定（分けて表示）

観測上の問題：受信できなかった便（地域差が大きい）、航跡開始時刻の欠落（約 9%）、航跡終了での代用、空港判定の不確実性（T1〜T4）、収集停止期間（2026年5月5日〜7日）。

シミュレーション上の仮定：空港・路線は完全に停止、代替運航を考えない、障害は仮想、時刻プロキシで判定、到達可能性はグラフ上のつながり。

2026年5月5〜7日にかかる期間では警告を出します。収集停止で観測便が少ないことは、シナリオの影響として数えません（影響は観測された記録からしか選ばれません）。

T1 だけのネットワークが「真のネットワーク」に近いとは限りません。受信局の少ない地域ほど便名の路線（T4）に頼っているため、T1 に絞ると地域の偏りが大きくなります。

## 10. 再現性

- シナリオのハッシュ（FNV-1a）は、結果に影響する項目（データセット、期間、モデル、評価時刻、有効なイベント（並べ替え済み）、条件）から作ります。イベント ID・名前・作成日時は含みません。
- 結果のキャッシュのキーはこのハッシュと分析期間です。
- CSV の各行にハッシュ・データセット・期間・条件を記録し、JSON のシナリオと対応させています。
