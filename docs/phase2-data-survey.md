# Phase 2 データ調査メモ

調査日：2026-11-10。数値は 2026年Q3ファイルの先頭 40万行（航空会社コード付きは約27.6万便）から取ったサンプルで、全体の傾向を見るための目安です。

## 1. 便データ：MrAirspace/aircraft-flight-schedules

| 項目 | 内容 |
| --- | --- |
| ライセンス | ODbL-1.0（データセット本体。README の文章・画像は対象外と明記） |
| 元データ | ADSBlol（ADS-B 受信網）。航路の補完に vradarserver の「便名→路線」データ、機材詳細に adsbdb.com を利用 |
| 配布形式 | GitHub Releases の Parquet。四半期ごと |
| 2026年に使えるファイル | Q1（840 MB）、Q2（912 MB）、Q3（1,027 MB）。Q4 は未公開（例年は翌年1月公開） |
| 規模 | Q3 で 16,018,874 便、16 行グループ |
| 列 | 全18列、すべて文字列型。欠損は `-`、検証ルートの欠損は `nan` |

つまり、2026年1〜9月の9か月分が使えます。10〜12月は Q4 の公開待ちです。

### 列の中身（実例）

```
TVF48ZM  LFML(地上ではなく800ft)  →  LGAT(2300ft)        検証ルート: LFML-LGAV
LOT6HU   EPWA(ground)            →  LRBS,LROP(ground)    検証ルート: EPWA-LROP
CUA5621  ZBAA,ZBAD,ZBNY(10875ft) →  ZBSJ,ZBYN(27600ft)   検証ルート: ZBAD-ZLLL
CES5339  出発側の記録なし          →  ZGSZ(5100ft)          検証ルート: ZSSS-ZGSZ
```

- `*_ApplicableAirports` は「航跡の端点の近く（約9km）にある空港」の候補リストで、複数入ることがあります。
- `*_FL_Ft` が `ground` なら地上の記録あり。数値なら、離陸後・着陸前の空中から記録が始まった（または途切れた）ということです。
- 1行目は、到着側の候補が閉鎖済みの旧アテネ空港（LGAT）になっています。端点が空港から離れていると候補がずれる例です。
- 3行目は、航跡の候補（ZBSJ/ZBYN）と検証ルート（ZLLL）が食い違っています。巡航中に記録が途切れた便です。

### サンプルでの割合（航空会社コード付きの便、出発側）

| ケース | 割合 |
| --- | --- |
| 出発側の記録なし | 10.0% |
| 地上から記録・候補1空港 | 36.3% |
| 地上から記録・候補複数 | 2.4% |
| 空中から記録開始（離陸を観測できていない） | 51.3% |
| 便名からの検証ルートあり | 84.7% |
| 地上・候補1空港なのに検証ルートと食い違う | 地上・候補1空港の便の 13.1% |

- 半数以上の便は離陸の瞬間を観測できていません。候補リストだけで空港を決めると誤りが多くなります。
- 検証ルートは便名から引いた「その便名の通常の路線」です。実際に飛んだ路線ではない可能性があるので、観測と食い違うことがあります（便名の使い回し、臨時便、ダイバートなど）。

### 四半期の重複

Q3 ファイルには 6月と10月の便も含まれていました（サンプル中それぞれ約2%）。README の指示どおり、**ファイルの対象月以外の便は捨てる**ことで重複を除きます。出発側の記録がない便は、到着時刻の月で判定します。

### 旅客／貨物の判定材料

専用の列はありません。使えそうなのは `AC_Type_Detailed` だけです（2026年Q1から追加）。

- `777F`、`747 8R7F`、`737NG 8ASBCF/W`（BCF＝貨物機改造）のように、貨物機と読める値があります。
- 一方で `737NG 85F/W` は「737-800、顧客コード 5F」で、**末尾の F が貨物を意味しない**例です。正規表現で機械的に判定すると誤ります。
- `AC_Type_Detailed` が `-` の便がサンプルの約45%あります。

## 3. 変換ルール案

### 対象とする便
- 航空会社コード（`Airline`）がある便だけを集計します。`-` の便（自家用機・訓練など）は件数だけ数えて品質レポートに出します。
- 出発空港と到着空港が同じ便（周回飛行など）は除外します。

### 空港の決め方（出発・到着それぞれ）

上から順に試し、最初に決まったもので確定します。どれでも決まらなければ `unknown` です。

1. **観測で確定**：地上から記録があり、候補が1空港
2. **観測＋位置で確定**：地上から記録があり、候補が複数。航跡の端点に最も近い空港を選び、2位との差が小さければ確定しない
3. **観測と検証が一致**：空中から記録が始まったが、検証ルートの空港が候補リストに入っている
4. **検証ルートのみ**：観測では決まらないが、検証ルートがある → 確定はせず `callsign` という根拠付きで別集計（後述）
5. それ以外は `unknown`

観測（1〜2）と検証ルートが食い違うときは観測を優先し、食い違いの件数を品質レポートに出します。

### 旅客／貨物
- **貨物**：機材詳細が、確認済みの貨物機リストに載っている型（777F、747-400F/-8F、767-300F、MD-11F、BCF/BDSF/SF/PCF/P2F などの改造機）
- **旅客**：機材詳細があり、上のリストに該当しない旅客機型
- **unknown**：機材詳細がない便、ビジネスジェット、軍用など

貨物機リストは推測で広げず、リポジトリ内の表（レビュー可能な CSV）として管理します。

### 公開データ
- 月ごとに「路線（空港ペア）× 方向 × 航空会社 × 分類」の便数を集計します。
- 空港の根拠（観測／検証ルート）ごとの件数も持たせ、UI で「観測で確定した便だけ」に切り替えられるようにする案です。
- 月ファイルが大きくなる場合（数十万レコード）は、JSON をやめて列指向の二進形式（例：ArrowやFloat/Uint配列のバイナリ）に変えます。

## 4. 決めてほしいこと

1. **検証ルートだけで決まる便を地図に出すか**
   - 出さない：観測で確定した便だけ。正確だが、離陸を観測できない地域（アジア・アフリカなど）の路線が大きく欠ける
   - 出す（区別して）：既定では含め、UI で「観測のみ」に切り替え可能にする ← おすすめ
2. **航空会社名の出典**：コード（例：RYR）だけ表示するか、名前の対応表を別の公開データ（ライセンス要確認）から取るか
3. **OurAirports のライセンス確認**：サイトの証明書が直ったら、データページの記載を一緒に確認してほしい
4. **ダウンロードの許可**：2026年Q1〜Q3 の Parquet 3ファイル（計約2.8 GB）を `data/raw/`（Git 管理外）に保存してよいか
