## 2. シミュレーションのデータモデル

`SimulationScenario`：`scenarioId`、`schemaVersion`、`name`、`description`、`datasetId`、`datasetVersion`、`baselineMode`（fixed／dynamic）、`simulationModel`（structural／temporal）、`analysisStart`、`analysisEnd`、`evaluationTime`、`events`、`filters`（区分、機材、最低便数、時刻基準、時刻プロキシ）、`analysisSettings`（有向、到達可能性の算法、中心性の算法、サンプル数、シード）、`createdAt`。

`SimulationEvent`：`eventId`、`eventType`、`enabled`、`startTimeUtc`、`endTimeUtc`、`targetType`、`targetIds`、`direction`、`parameters`、`sourceType`（hypothetical／reported）、`sourceReference`。

実装したイベント：`AIRPORT_CLOSURE`、`MULTIPLE_AIRPORT_CLOSURE`、`ROUTE_SUSPENSION`（有向・双方向）。予約した種類（`CAPACITY_REDUCTION`、`COUNTRY_DISRUPTION`、`AIRLINE_WITHDRAWAL`、`AIRSPACE_RESTRICTION`、`WEATHER_DISRUPTION`、`SAFETY_ADVISORY`）はファイルに保持できますが、適用せず、UI からも作れません。安全勧告は閉鎖ではないので何も取り除きません。

## 3. Structural Simulation の定義

基準期間のネットワークから、停止した空港の該当する側（出発・到着）の便と、停止した路線の方向を取り除きます。固定の基準では評価時刻に有効なイベント（評価時刻なしなら期間と重なるイベント）、時間窓に連動では窓と重なるイベントを適用します。値は「その期間中ずっと使えないと仮定した状態」についてのもので、期間中の便が実際に欠航したことを意味しません。

## 4. Temporal Disruption の定義

集計前の便の記録ごとに、時刻が停止区間 [start, end) に入るかを判定します。出発側は航跡開始、到着側は航跡終了（`endpoint`、既定）、または両方とも基準時刻（`reference`）。路線の停止は基準時刻で判定します。複数のイベントに該当する便も1便です。結果は「仮想的な影響対象の観測便数」で、欠航便数ではありません。

**Phase 9B の案の検証**：Phase 9B では、シナリオの変換を「集計結果」と「描画・研究用データへの変換」の間に入れる案を示しました。集計結果（路線×方向×航空会社×区分×分類の便数）には時刻がないため、24時間の窓から6時間分の便だけを正しく除くことはできません。そこで、時刻照合は集計の前（Web Worker の `WindowAggregator.addDay`）で便ごとに行い、影響対象の便を別の集計として持つ構造に変えました。全体の集計から影響対象の集計を引いたものがシミュレーション後のネットワークです。構造モデルは時刻を使わないため、集計後の行に適用します。

## 5. 時刻精度と限界

- 判定は分単位です（日別ファイルの基準時刻が分単位のため）。区間の境界が分単位なら、秒単位の時刻で判定した場合と同じ便が選ばれます。秒単位の結果は表示しません。
- 公開用データには基準時刻しかなかったため、空港の到着側を判定できませんでした（例：停止の前に出発して停止中に到着した便）。研究用 Parquet の航跡終了時刻から、日別ファイルと同じ順序の補助ファイル `temporal/endpoints/` を作りました。
  - 全 273 日で、日別ファイルの便の並びとの一致を生成時に照合しています。
  - 2,290 万便のうち航跡終了が分かるのは 1,993 万便（開始時刻がない便 204 万、終了時刻がない便 94 万）。
  - 容量：77.7 MB（gzip 26.7 MB、1日あたり約 98 KB）。生成時間：約 46〜51 秒。
  - 時刻照合で空港を停止するときだけ読み込みます。ほかの機能には影響しません。
- 航跡の開始・終了は離着陸時刻ではありません。停止した側の時刻がない便は、もう一方の時刻からみて入りうる場合（航跡は最長 24 時間と仮定）に「判定不能」として数え、除外しません。
- 分析の対象は基準時刻が分析期間に入る便です。期間の前に基準時刻があり期間中に到着する便は、分析期間を長くしないと含まれません。

## 6. イベント重複の扱い

空港の出発側・到着側、路線の各方向ごとに、停止区間の和集合を作ってから判定します。順序の入れ替え・同じイベントの重複・無効化・不正なイベント（存在しない空港、観測されていない路線、終了 ≤ 開始、未対応の種類）をテストで確認しています。不正なイベントは理由を表示して適用しません。将来の非可換な操作（容量削減率など）の適用順は methodology に記しました。

## 7. Fixed / Dynamic Baseline

- 固定：基準期間の観測ネットワークは変わりません。評価時刻を動かすと、有効なイベントだけが変わります（テスト D）。
- 時間窓に連動：タイムラインの各時間窓で、同じ窓の観測ネットワークに障害を適用し、同じ窓の観測と比べます（テスト E）。再生中は軽い指標だけを計算し、接続性は一時停止の後に計算します。

## 8. 計算した影響指標

直接の影響（停止した空港、接続を失ったほかの空港、失われた直接接続（無向・有向）、便数の減った接続、影響対象の観測便数、航空会社コード別、出発空港の地域・国別）。接続性（到達可能な組、1・2・3ホップ以内、ネットワーク効率、弱連結成分と最大成分、経路のなくなった組、ホップ数の変化の内訳）。空港別（接続先、到達可能、2・3ホップ以内、到達不能になった相手、経路が長くなった相手と増えたホップ）。

ネットワーク効率は無重み最短経路で、Research Mode の調和近接中心性（正規化）の全空港平均と同じ定義です（テストで一致）。

## 9. Total Impact と Spillover Impact の違い

- システム全体：基準ネットワークの全空港（停止した空港も孤立した空港として残す）の組。前後で分母が同じ。
- 波及：停止対象以外の空港の組（停止した路線の組を除く）。障害前は停止対象を経由する経路も使えます。前後で同じ空港集合。

空港をノード集合から除くと分母が変わり効率が見かけ上上がることがあるため、どちらも前後で同じ集合を使います。手計算できる小さなグラフでテストしています（例：A–B–C–D と E–B で B を停止：全体の効率 0.667→0.100、波及 0.528→0.167）。

## 10. 代替経路分析

選んだ空港の組について、中継空港を共有しない最短経路を最大3つ（障害前・後）。空港を選ぶと、到達できなくなった相手と経路が長くなった相手を一覧し、相手を押すとその経路を地図に表示します。経路を失った組の全一覧は CSV で出力します。グラフ上の経路で、実際の乗り継ぎ便ではありません。

## 11. 地図・地球儀での表示

既存のレンダラーと GPU バッファを再利用し、比較表示の色（減少＝オレンジ、消失＝オレンジの破線、変化なし＝薄い灰色）を使います。追加は空港の状態1つ（停止した空港：赤い点）と、停止した路線の太線（既存の暖色 `#ffd27a`）だけです。表示は「前後を重ねる」「障害後」「障害前」。構造（利用できないと仮定した接続）と時刻照合（期間中の便がなくなった接続／便数が減った接続）で凡例の文言を変えています。2D と 3D で同じシナリオ・同じ件数（テスト J）。

## 12. Research Mode との統合

分析条件に `scenario` を追加し、同じ適用処理で作ったネットワークに既存の指標を計算します。シミュレーションのパネルから開くと、比較タブで障害前（観測）と比べられます。空港が除かれてノード集合が違う場合、密度とクラスタ係数の増減率は表示しません。`scenario` のない条件のハッシュは変わりません。

## 13. シナリオ保存・復元

JSON（シナリオ全体）を保存・読み込みでき、読み込み時に形式、スキーマの版、データセット ID・版、期間、イベントの種類、空港・路線、時刻を検証します。結果の JSON には、シナリオ、ハッシュ、分析期間、算法（厳密な探索、近似なし）、主な指標を記録します。CSV（ネットワーク指標、空港別、路線別、失われた経路、地域・国・航空会社別）は各行にハッシュ・データセット・期間・条件を持ちます。短いシナリオは URL（`sim=1&sev=...`）に入り、1,500 文字を超えるイベントは URL に入れません。

## 17. 未解決の問題

- 補助ファイル（77.7 MB）がリポジトリと GitHub Pages の容量を増やします。GitHub Pages で gzip が使われることは日別ファイル（JSON）で確認済みで、同じ JSON 形式にしています（公開後の確認はまだ）。
- 分析期間の前に基準時刻がある便は、期間中に到着しても対象外です（分析期間を長くすれば含まれます）。
- 航跡は最長 24 時間という「判定不能」の範囲の仮定は、数え方にだけ使い、除外の判定には使っていません。
- 描画フレームの時間は計測していません（ブラウザの画面が非表示の状態で計測したため）。
- 「影響の大きいほかの空港」の並び順は「到達不能になった相手→2ホップ以内の減少→接続先の減少」の順で、指標を選んで並べ替える機能はありません（CSV で全空港を出力できます）。
- 地図上の路線の選択は既存の操作（路線のクリック）に頼っています。大量の路線を一度に停止する操作はありません。

## 18. Phase 9D への引き継ぎ

- イベントの追加：`model.ts` の予約済みの種類に、`disruption.ts` の和集合と同じ形で適用処理を追加します。容量削減などの非可換な操作は、停止の和集合の後に、methodology に記した順序で適用します。
- タイムライン：イベントは開始・終了を持ち、`structuralState`（時刻・期間）と `matchFlight`（記録）が評価を担います。専用の編集タイムラインはこれらを使えます。
- 段階的な障害・復旧：1つの空港に複数の区間を持てます（和集合で処理）。容量の段階は `parameters` を使う予定です。
- 地図：空港の「停止」状態と停止した路線の太線があります。発生・拡大・復旧の表示はこれを時刻で切り替えます。
- 再生：時間窓に連動する基準で、各ステップ 20〜50 ms です。接続性（数秒）は再生中には計算しないので、9D でもこの分担を保ちます。
