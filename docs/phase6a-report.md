## 1. 修正した不具合

### H2：機材分類の取りこぼし（`pipeline/classify_aircraft.py`）

型式（`AC_Type`）と型番の詳細（`AC_Type_Detailed`）が同じ機材かを確かめる処理が、A320neo ファミリー（A19N／A20N／A21N）や 737 MAX の型番表記を読めず、旅客機を大量に「不明」にしていました。

- 型番の詳細を「メーカー・ファミリー・モデル・シリーズ・世代」に分解して照合するように書き直しました。
- 737 MAX は貨物型が存在しないため、型番の詳細がなくても旅客にしています。
- 型式と型番の詳細が本当に食い違う便は、これまでどおり「不明」です。
- 分類表 `pipeline/reference/aircraft_variant_class.csv` を作り直しました（旧版は `pipeline/reference/archive/` に保存）。どの行にも適用したルール名が入っています。

**分類は機材の分類であって、その便が実際に旅客を運んだかどうかではありません。** 旅客機による貨物専用便（いわゆる「旅客機での貨物輸送」）は旅客に入ります。

分類表のうえでの変化（航空会社コードがない便も含む元データ全行の便数で重み付け）：

| 変化 | 便数 |
| --- | --- |
| 不明 → 旅客 | 2,884,702 |
| 旅客 → 不明（型式と型番の詳細が矛盾） | 11,989 |
| 貨物 → 不明（同上） | 21 |

### H1：同じ空港が別のコードで二重に数えられる（`pipeline/airports.py`、新規）

旧版では、OurAirports の同じ空港（同じレコード）の旧コードや GPS コードが、別々の空港として地図に出ていました。

- OurAirports の**同じレコード**を指すコードだけを1つの空港にまとめます。IATA コードが同じというだけでは統合しません。
- 1つのコードが複数のレコードに当てはまる場合は優先順位（ICAO > ident > GPS、空港の規模）で1つを使い、「未解決」として `research/airport_aliases.csv` に残します。
- 統合したコード：82、未解決のコード：7（FAER、OIBH、OPGD、WAMK、WRLB、WIOD、ZPZT）

**KPBI／KDJT**：OurAirports のレコード 3766 は現在 ICAO KDJT／IATA DJT（改称後の名称）を載せていますが、公式の ICAO／IATA の資料で確認できていません。便データの空港推定は KPBI を 74,066 回、KDJT を 102 回使っています。同じレコード・同じ座標なので1つの空港にまとめ、表示上のコードは確認が取れるまで KPBI／PBI のままにしています（`pipeline/reference/airport_canonical_overrides.csv`、状態 `label_unverified`）。

**作業中に見つけて直した不具合**：空港の表示コードがレコードごとに一意になっていませんでした。あるレコードの ident が別の空港の ICAO コードと同じ場合（OIBH：Bastak と Bahregan、ZPZT：旧昭通空港と新空港）、`airports.json` に同じ ID が2つ出ていました。表示コードは「そのコードで実際に引けるレコード」だけが使い、もう一方は自分の ident（それも他の空港を指すなら `OA<OurAirports ID>`）にするよう直しました。地図の便数・路線は修正の前後でバイト単位まで同一で、変わったのは空港一覧の重複2件、テレマコ・ボルバ空港の表示コード（SSVL → SBTL。SSVL は別の飛行場のコード）、地域別カバレッジの二重計上です。合成データのテストを追加しています。

### 空港判定の根拠を R1〜R5 に分割

旧版の「観測」は、航跡だけで決まった空港と、航跡の候補と便名の路線が一致した空港をまとめていました。出発・到着の端ごとに次のルールを記録するようにしました。

| ルール | 意味 |
| --- | --- |
| R1 | 航跡の端が地上か 3,000ft 以下で、空港候補が1つ |
| R2 | 同じ条件で候補が複数 → 最も近い空港（2位との差が 1km 以上） |
| R3 | 便名の路線の空港が航跡の候補に含まれる（航跡の端が上空でも可） |
| R4 | 便名の路線だけ |
| R5 | 判定不能 |

便ごとの信頼度は両端から決めます：T1＝両端 R1/R2 で不一致なし、T2＝両端 R1/R2 だが便名の路線と不一致の端がある、T3＝R3 の端があり R4/R5 はない、T4＝R4 の端がある、X＝R5 の端がある。

地図（Explore Mode）の「観測／便名から推定」は従来どおりで、T1〜T3 が「観測」、T4 が「便名から推定」です。研究用の集計表 `research/routes_monthly.parquet` には端ごとのルールと信頼度が入っています。

**注意**：「航跡由来」は「確実」を意味しません。端点の近くに空港が1つあっても、上空通過や近くの別の飛行場の可能性は残ります。また、**T4 の誤り率は測れません**。便名の路線と航跡が両方ある便での不一致率（下の 1,889,200 便）を、航跡がない便の誤り率として使うことはできません。

### 再現性

- `pipeline/inputs.lock.json`：入力4ファイル（四半期 Parquet 3本と OurAirports の airports.csv）のバイト数と SHA-256、リリース名、取得日時。生成時に照合し、一致しなければ止まります。
- `provenance.json`：データセット ID・バージョン、生成時刻、ルールのバージョン（`2026.11-r2`）、スキーマのバージョン、Git コミット、パイプラインに未コミットの変更があるか、Python・DuckDB のバージョン。
- 便 ID は入力の内容だけで決まる並び順で振るので、同じ入力からは同じ出力になります（テスト済み）。
- 既存のデータセットのフォルダが空でなければ、上書きせずに止まります。v1（`public/data/observed-2026/`）には一切手を入れていません。

### 観測範囲（カバレッジ）の検出

`research/coverage_daily.csv` に日別・地域別（大陸）の便数を出し、同じ曜日の前後28日の中央値の 0.8 倍を下回った日に `suspected_low` の印を付けます。**検出だけで、補正や補完はしていません**。印の付いた日が実際に欠けているとは限りません（祝日や運航の変化でも下がります）。

世界全体で印が付いた日：2026-01-23、05-05〜07、06-11、08-01、08-09、08-13。`manifest.json` の各月に `suspectedLowDays` として入れていますが、UI にはまだ表示していません。

変化の説明：

- **便数 −59／出発＝到着 +59**：コードの統合で、旧コードから新コードへ飛んだことになっていた便が「同じ空港の発着」になり除外されました。総数（航空会社コード付き 26,862,421 便）は変わっていません。
- **旅客と不明**：H2 の修正による移動です。貨物の −1 は型式と型番の詳細が矛盾する便です。
- **観測 +7,405／便名から推定 −7,464**：空港候補の重複（同じ空港の別コード）を1つにまとめたため、「候補が複数」で決められなかった端の一部が R1／R3 で決まるようになりました。
- **空港 −9、路線 −80、航空会社コード −1**：同じ空港の二重登録が解消された分です。航空会社コードの −1 は CCE で、v1 での便は HEAX–HEBA の9便だけでした。HEBA は HEAX と同じ OurAirports のレコード（ボルグ・エル・アラブ空港、HBE）なので、v2 では同じ空港の発着として除外されています。
- **容量 +11 MB**：研究用ファイル（`research/`、Parquet 10.4 MB など）の追加分。ブラウザが読む月別ファイルはほぼ同じです。

主要空港（1〜9月の発着便数）は KATL、KORD、KDFW、KDEN、EGLL、LFPG、EHAM、EDDF、LTFM、OMDB、RJTT、WSSS、VHHH、ZBAA、YSSY、SBGR のすべてで **v1 と完全に同じ**です。接続空港数（8月）は KATL 356 → 355、KORD 562 → 561 で、それ以外は同じ（統合された小空港への路線が1本にまとまったため）。

## 4. 未解決の課題

1. **KPBI の表示コード**：KDJT／DJT への改称を公式資料で確認できていません。確認できたら override を更新します。
2. **未解決のコード 7件**（FAER、OIBH、OPGD、WAMK、WRLB、WIOD、ZPZT）：1つのコードが複数の空港に当てはまります。優先順位で1つを使っていますが、正しいとは限りません。
3. **T4（便名のみ）の信頼性**：誤り率として測る方法がありません。地図ではこれまでどおり区別して表示しています。
4. **カバレッジの補正**：検出だけです。少ない日をどう扱うか（除外・補正・注記）は決めていません。
5. **旅客／貨物は機材の分類**：便の目的（旅客便か貨物便か）ではありません。不明は 2,697,019 便（地図に載る便の 11.8%）残っています。
6. **研究用ファイルは UI に出していません**：R1〜R5、T1〜T4、カバレッジの印は `research/` と品質レポートにだけあります。
7. **OurAirports の利用条件**：サイトの証明書エラーのため、原文を確認できていません（Phase 5 から継続）。
8. **生成時間**：全9か月で約33分。大半は便 ID を振るための全件ソートです。
9. **リポジトリの容量**：v1 と v2 の両方を置いているため、公開データは約108 MB です。v1 をいつ外すかは未定です。
